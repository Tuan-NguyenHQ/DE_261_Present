⚙️ Cơ chế

  • Mỗi bước là 1 subprocess (spark-submit / dbt), fail → dừng các bước sau
  • Spark job in dòng PIPELINE_METRICS={json} → orchestrator parse
  • Ghi audit vào analytics.pipeline_runs: run_id, step, status, rows, error, details

🔁 Idempotent ở mọi layer

  • Lake: ghi đè đúng partition dt=YYYY-MM-DD
  • Staging: ALTER TABLE … DELETE WHERE _batch_date = D rồi mới insert
  • Fact: dbt incremental delete+insert theo unique_key
  • Dim / report: build lại từ toàn bộ lịch sử, surrogate key ổn định

"Đọc được gì giữ nấy" — schema-on-read, không ép kiểu

Xử lý

  • Đọc CSV (header) & XML (rowTag) với mọi cột = string

STAGING  silver → ClickHouse (load_clickhouse.py)

Nạp theo contract cột · idempotent · đối soát số dòng

Quy trình cho mỗi entity

  1. Đọc silver/<entity>/dt=D, kiểm tra đủ cột theo contract
  2. Điền default cho cột NOT NULL (booking_channel → 'Other', …)
  3. ALTER TABLE staging.X DELETE WHERE _batch_date = D (mutations_sync)
  4. Ghi qua JDBC (batch 10.000)
  5. Reconciliation: count() ClickHouse = số dòng silver, lệch → fail

Vì sao ClickHouse?

  • OLAP cột, nén mạnh, tổng hợp hàng triệu dòng trong ms
  • ReplacingMergeTree + FINAL để dedup theo phiên bản
  • ASOF JOIN → tra version SCD2 / tỷ giá theo ngày
Bảng stagingEngine · ORDER BYÝ nghĩa

SCD Type 2: lưu lịch sử thay đổi của dimension

Nguồn: snapshot hằng ngày trong staging.hotels → chỉ giữ ngày có thuộc tính thay đổi

Thuật toán (dim_hotels / dim_customers)

  1. attr_hash = cityHash64(name, tier, star, city, …)
  2. So với hash ngày trước (lagInFrame)
  3. Khác → bắt đầu version mới, valid_from = _batch_date
  4. valid_to = ngày trước version kế tiếp, version cuối = 9999-12-31
  5. hotel_sk = cityHash64(hotel_id, valid_from) → ổn định qua các lần build

Fact tra đúng version

ASOF LEFT JOIN dim_hotels h
  ON  b.hotel_id = h.hotel_id
  AND b._batch_date >= h.valid_from

Chất lượng dữ liệu theo từng lớp

"Defense in depth" — mỗi layer chặn một loại lỗi

Bronze

  • Schema contract (cột bắt buộc)
  • Phát hiện schema drift
  • Dòng hỏng → rejected

Silver

  • DQ rule theo entity
  • Dedup theo business key
  • Circuit breaker > 20%

Staging

  • Contract cột silver ↔ CH
  • Reconciliation số dòng
  • Idempotent delete

Gold · dbt test

  • unique / not_null / relationships
  • accepted_values
  • SCD2 integrity

dbt test: error vs warn

  • error (chặn pipeline): PK trùng, FK không tồn tại trong dim, SCD2 chồng lấn
  • warn (báo cáo): fact gắn unknown member, payment orphan, thiếu tỷ giá
  • join_use_nulls = 1 → LEFT JOIN không khớp ra NULL thật, test có ý nghĩa
